# Phase 2 — Authentication, Database, and Translation Engine

## النطاق

تضيف هذه المرحلة أول طبقة تشغيل فعلية بعد أساس Phase 1. يعتمد تطبيق الويب الحالي على قالب Manus الكامل المبني على React وExpress وtRPC وDrizzle، مع مصادقة Manus OAuth وجلسة موقعة على الخادم. لذلك تم توسيع الأساس الموجود بدل إنشاء نظام مصادقة ثانٍ قد يسبب جلسات متعارضة أو إعادة بناء غير ضرورية.

## Authentication

يستمر تسجيل الدخول عبر Manus OAuth. بعد التحقق من جلسة المستخدم، يقوم `sdk.authenticateRequest` بمزامنة المستخدم مع جدول `users`، بينما يفرض `protectedProcedure` وجود مستخدم مصادق عليه قبل تنفيذ الإجراءات الحساسة.

أضيفت كذلك مسارات REST محلية في `server/authRoutes.ts`: التسجيل، الدخول، الخروج، refresh، وcurrent-user. تستخدم الحسابات المحلية scrypt مع salt عشوائي، access token قصير العمر داخل cookie الجلسة التي يفهمها `sdk`، وrefresh token مدورًا لا يُحفظ خامًا. لا تتعامل الواجهة مع password hashes أو مفاتيح التوقيع.

أضيف الإجراء `auth.bootstrap` في `server/routers.ts`. يضمن هذا الإجراء وجود مساحة عمل شخصية للمستخدم، ثم يعيد المستخدم ومساحة العمل وقائمة العضويات. لا يتعامل العميل مع ملفات تعريف الارتباط أو مفاتيح الجلسات مباشرة.

## Database

أضيفت الجداول التالية إلى `drizzle/schema.ts`:

| الجدول | الغرض |
|---|---|
| `organizations` | مساحة عمل يملكها مستخدم، مع اسم وslug فريدين. |
| `organizationMembers` | ربط المستخدمين بمساحات العمل مع أدوار `owner` أو `admin` أو `member`. |
| `passwordCredentials` | تخزين hash كلمة المرور فقط لكل مستخدم محلي. |
| `refreshTokens` | تخزين hash للرموز المتجددة مع expiry وrevocation وrotation. |
| `translationHistory` | قياس الاستخدام والـ latency وحالة الطلب دون تخزين نص الترجمة افتراضيًا. |

تستخدم النسخة الحالية اصطلاحات Drizzle الموجودة في Phase 1، بما في ذلك مفاتيح عددية متزايدة وجداول MySQL/TiDB. هذا قرار توافق مقصود؛ تحويل الجداول القائمة إلى UUID أو PostgreSQL في هذه المرحلة سيكسر علاقات الاجتماعات والهجرات الحالية دون فائدة تشغيلية مباشرة.

أنشئت migration رقم `0004_dark_leo.sql` للمؤسسات والعضويات، و`0005_flat_omega_sentinel.sql` لبيانات الاعتماد والجلسات وسجل الترجمة. يلزم تطبيقهما على قاعدة البيانات المستهدفة قبل استخدام المسارات الجديدة في بيئة تشغيل حقيقية؛ لم تُطبّقا محليًا لأن `DATABASE_URL` غير متاح في بيئة التنفيذ الحالية.

## Translation Engine

أعيد تنظيم الترجمة حول العقد التالي:

```ts
interface TranslationProvider {
  translate(request: TranslationRequest): Promise<TranslationResult>;
}
```

التنفيذ الأول هو `ManusLlmTranslationProvider`. يعمل بالكامل على الخادم، يكتشف نموذجًا متاحًا من قائمة النماذج، ويرسل النص داخل حدود واضحة على أنه محتوى غير موثوق. يعيد المحرك النص المترجم واسم المزود والنموذج المستخدم. عند تطابق لغة المصدر والهدف، يستخدم النظام passthrough دون استدعاء خارجي.

يتم اختيار المزود من `TRANSLATION_PROVIDER`، والقيمة الافتراضية هي `manus-llm`. لا تظهر مفاتيح البوابة أو بيانات الاعتماد في العميل أو في السجلات. يمكن إضافة مزود آخر لاحقًا من خلال تنفيذ العقد نفسه دون تغيير إجراءات tRPC أو واجهة المستخدم.

## الاختبارات وCI

أضيفت اختبارات لمسار `auth.bootstrap`، بدائيات المصادقة المحلية، endpoint الترجمة، وخدمة الترجمة باستخدام مزود اختباري داخل الاختبارات فقط. كما تم تحديث اختبارات تكامل قديمة كانت تشير إلى مسار تطبيق الهاتف السابق `linguabridge-mobile/` رغم أن البنية الحالية تستخدم `mobile/`. أضيف workflow للويب يشغّل lint وtypecheck وmigration consistency والاختبارات والبناء وتدقيق التبعيات.

## تشغيل Phase 2

بعد ضبط متغيرات البيئة، نفّذ ما يلي من مجلد `web/`:

```bash
pnpm install --frozen-lockfile
pnpm drizzle-kit migrate
pnpm check
pnpm test
pnpm build
```

لا ينبغي وضع قيم حقيقية في `.env.example` أو في Git. يجب توفير `DATABASE_URL` و`JWT_SECRET` وإعدادات Manus OAuth وبوابة LLM من خلال مدير أسرار بيئة التشغيل.

## القيود المعروفة

لا يمكن تأكيد استدعاء ترجمة خارجي من هذه البيئة لأن `BUILT_IN_FORGE_API_KEY` غير مضبوط محليًا. الاختبارات الحالية تتحقق من العقد، والمسارات، والتفويض، والتعامل مع النص، لكنها لا تدّعي نجاح ترجمة خارجية حية. كما أن تطبيق migration يحتاج إلى قاعدة البيانات المستهدفة وبيانات اعتمادها. يستخدم CI تدقيق التبعيات مع السماح باستمرار workflow مؤقتًا لأن الشجرة الحالية ما زالت تحتوي advisories عالية وحرجة تحتاج معالجة مستقلة.
